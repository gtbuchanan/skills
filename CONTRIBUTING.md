# Contributing

## Prerequisites

- [mise](https://mise.jdx.dev) — pins every tool this repo needs (node, hk, pkl, actionlint, shellcheck, shfmt) and installs the git hooks.
- Docker (Docker Desktop) — for `pnpm eval:docker` and the results server. Not needed for `pnpm eval`.
- A logged-in Claude Code session for keyless eval auth (`~/.claude/.credentials.json`), or an `ANTHROPIC_API_KEY`.

## Setup

1. `mise trust && mise install` — installs the pinned tools and, via the `postinstall` hook, the hk git hooks.
1. `pnpm install`
1. `pnpm skills:sync` — copies `skills/*` into `.claude/skills/` so Claude Code (and other agents) can load them. Re-run after editing a skill: on Windows these are copies, not symlinks.

## Repository layout

- `skills/<name>/SKILL.md` — the skills. This is the cross-agent source of truth. Everything here is distributed with the skill, so nothing test-only belongs in it.
- `.claude/skills/`, `.agents/skills/` — generated copies (gitignored); regenerated by `pnpm skills:sync`.
- `evals/<name>/` — the eval suite for skill `<name>`, kept outside `skills/` so it is never distributed.
- `scripts/` — the eval harness runners.
- `artifacts/`, `dist/` — generated output, incl. the results server's data (gitignored).
- `turbo.json`, `mise.tasks.toml`, `tsconfig.json`, `tsconfig.build.json` — generated by `gtb sync`; edit `tsconfig.base.json` (hand-authored) instead. One exception: `evals/**` is added by hand to the `lint:eslint` and `typecheck:ts` inputs, because the generator's input lists don't know about `evals/`. Without it an evals-only edit doesn't invalidate those caches and turbo skips the tasks. **`gtb sync` rewrites `turbo.json` and will drop both — re-add them** until the generator covers `evals/`.
- `evals/package.json` — not a workspace package (the workspace declares no `packages` globs, so nothing installs from it). It exists to give the harness a `#lib/*` subpath import mapping, and must mirror the root's `type` and `engines`: the nearest manifest is what decides module format and what `eslint-plugin-n` treats as the supported Node range.
- `evals/tsconfig.json` — hand-authored, not generated. It puts the harness in a TypeScript project (so the ESLint project service can parse it), sets `allowImportingTsExtensions` because the harness imports `.ts` paths directly, and keeps `checkJs` on for the one remaining `.cjs` double. The root `typecheck:ts` script runs `tsc` against it as a second pass; `gtb sync` preserves existing script values, so that survives.
- `mise.lock` — generated by `mise lock`, and committed: CI installs tools with `MISE_LOCKED=1` and refuses anything the lockfile doesn't pin.

## Shared tooling

Build, lint and hook configuration comes from
[gtbuchanan/tooling](https://github.com/gtbuchanan/tooling). `@gtbuchanan/cli`
(`gtb`) owns the generated config, `@gtbuchanan/eslint-config` supplies the lint
rules — including the Agent Skills spec checks over every `SKILL.md` — and
`hk.pkl` extends the shared hk preset.

| Command                          | Purpose                                                  |
| -------------------------------- | -------------------------------------------------------- |
| `pnpm lint:eslint`               | eslint over the whole repo; add `--fix` to autofix       |
| `pnpm typecheck:ts`              | `tsc --noEmit`                                           |
| `mise run hk:all`                | run every pre-commit hook across all files (the CI gate) |
| `pnpm verify`                    | check the generated config for drift                     |
| `pnpm exec gtb sync`             | regenerate `turbo.json`, tsconfigs, scripts, mise tasks  |
| `pnpm exec gtb turbo run <task>` | run an aggregate task (`check`, `build`)                 |

The aggregates have no root script by design: with the root as the only package,
turbo would resolve `pnpm check` back to the script that invoked it and abort on
its recursion guard. Dispatch them through `gtb turbo run` instead — `gtb verify`
fails if a root script shadows an aggregate again.

On Termux, changing the dependency graph needs `pnpm install --force` once —
pnpm re-checks platform support from the lockfile before `.pnpmfile.cjs` gets a
chance to ungate the two android-blocked packages in promptfoo's tree. Plain
`pnpm install` works on every other host and on any later run.

## Authoring a skill

- One skill per directory: `skills/<name>/SKILL.md` with YAML frontmatter (`name`, `description`). The description is the trigger — say what it does and when to use it.
- Mark building blocks that shouldn't be user-invoked with `user-invocable: false`; Claude can still compose them.
- Prefer composition (a thin orchestrator that delegates) and pure, side-effect-free cores — they're easier to test.
- Lint enforces the [Agent Skills spec](https://agentskills.io/specification): frontmatter schema, `name` matching the directory, resolvable file references, and a 500-line cap on `SKILL.md`.

## Running evals

Pick a runner:

- `pnpm eval` — one process per skill, on this host. The default, because it needs nothing but Node and so works anywhere, including hosts where Docker cannot run.
- `pnpm eval:docker` — one container per skill, reporting to a local promptfoo server. Run `docker compose up -d` once, then browse <http://localhost:3000> for the shared results.

Each takes a skill filter and forwards promptfoo flags: `pnpm eval <skill> --repeat 3`. Repeats are independent samples only for a suite that empties its call log per test — see [Authoring an eval](#authoring-an-eval) — since a checker asserting over one shared, append-only log can otherwise be satisfied by an earlier repeat's calls.

They rest on the same guarantee, which was never kernel-level even in the container: real provider CLIs are _absent_, so a command a suite forgot to stub fails with command-not-found instead of quietly hitting production. The container gets that from its own image, which simply never installs them. The native runner reconstructs it — a PATH allowlist, a stub dir at the front of PATH with every provider CLI shadowed, a clean `HOME` holding only the credentials, and a per-suite workspace holding only that suite's skills — and a self-test runs first, aborting if any provider CLI is still reachable.

- `node scripts/check-isolation.ts` reports what the native runner would admit, without launching an eval. Worth running from whichever shell you invoke `pnpm eval` in — the ambient PATH is shell-dependent.
- Which tools are admitted, and which are shadowed, is declared in `scripts/eval-isolation.ts`. A skill that shells out to a new provider CLI belongs in that list, or the suites keep it reachable.

Auth: each reads `~/.claude/.credentials.json` when present (keyless), otherwise forwards `ANTHROPIC_API_KEY`. The native runner links that file into each suite's clean `HOME`, so a token refresh mid-run persists; the container bind-mounts it read-write for the same reason. Behind a TLS-inspection proxy, export the proxy's root CA to `artifacts/ca-bundle.pem` and it's trusted automatically.

## Authoring an eval

A suite lives in `evals/<name>/`, outside the skill it exercises — `skills/<name>/` is copied verbatim into every deployed and published skill, so test doubles, fixtures and harness config must not live there:

- `promptfooconfig.yaml` — uses the `anthropic:claude-agent-sdk` provider with `setting_sources: ['project']` and `skills: ['<name>']` so it exercises the real skill; scope `append_allowed_tools` to the minimum. Assert `skill-used` plus a `javascript` checker over the output.
- `fixtures/` — inputs the agent reads.

Checkers and setup extensions are TypeScript ES modules (`export default` / `export const extensionHook`) and parse everything they read — call logs, fixture JSON, promptfoo vars — through a [valibot](https://valibot.dev) schema, so a malformed input fails with a readable reason instead of an `undefined` deref.

Two runtimes load this code, which constrains what it may contain. promptfoo registers `tsx` when a `file://` module ends in `.ts`, so checkers and extensions get full TypeScript. The stubs are different: the runner execs them with plain `node`, whose type stripping only erases annotations. **Keep the whole harness to erasable syntax** — no enums, no namespaces, no parameter properties — and import type-only symbols with `import type`. Import specifiers name the real file (`#lib/paths.ts`), because neither runtime rewrites `.js` back to `.ts`.

For a skill that calls an external CLI, mock it instead of hitting the network:

- Ship `evals/<name>/bin/<cmd>-stub.ts` — a fake CLI that logs its argv to `$STUB_LOG` and returns canned output. Either runner installs it as `<cmd>` at the front of the eval `PATH`, and the real one is unreachable either way: absent from the container image, shadowed on the native path.
- A `setup.ts` beforeAll extension sets `STUB_LOG` (and truncates it per run, via `resetCallLog`).
- The checker asserts against the logged calls. These suites run only under the harness — a suite that overlays files into a skill tree calls `requireHarness` and refuses a hand-run `promptfoo eval`.

What the stubs get wrong easily:

- **The fall-through is an answer.** Empty output with exit 0 does not read as "I don't know" — it reads as "there is nothing here", and an agent will act on it. The best way to win that is not to play: where the real tool is safe to run offline, seed real state and let the stub only record what was asked. `evals/gtb-pr-review-diff` seeds a genuine checkout (`seed.ts`) with a local bare origin, so `log`, `diff`, `status` and even `fetch` are true by construction and its `git` double is a passthrough. Where the real thing can't be reached — `gh`, `az` — keep the canned facts in one module every stub reads, and make an un-canned command fail loudly rather than succeed silently.
- **Canned data can't name what it doesn't control.** A fixture that has to reference seeded state (a commit, an id the real tool minted) should name it symbolically and be resolved at setup — `evals/gtb-pr-review-diff/fixtures/scenario/reviews.json` names commits as `{{ sha:<plan key> }}`, and an unknown key throws instead of resolving to nothing.
- **`--repeat` shares the log.** promptfoo fires `beforeAll` once per eval, not once per test, so every repeat appends to the same file. A checker that asserts over the whole log (`some`/`every`, rather than ids unique to one test) must also truncate in `beforeEach` (`truncateCallLog`) or its repeats are not independent samples. Per-test truncation is race-free only in a serial suite (`maxConcurrency: 1`); a concurrent one needs one log per test instead — `STUB_LOG_DIR`, as `gtb-resolve-azp-deployment-backlog` keys one per pipeline id.
